# Parent-owned cloud dispatch

The ledger owns packet preparation, local ownership, lifecycle observations, evidence submission and acceptance gates. The trusted parent owns actual cloud_threads task creation, reading, messaging and cancellation through its supported platform tools. This module never creates a remote task, uses credentials or launches Codex locally. A CLI launch would be a separate execution route.

## CLI lifecycle

Set PLAN_LEDGER_DB explicitly for the intended ledger. cloud_dispatch_prepare requires a stable client_key, one step_id in an active plan, and the same authorization/scope/context fields as planner_packet. It persists the packet and returns prepared with no remote identity or lease. Retrying the same client_key recovers the request. A different key cannot create a second active request for that step.

cloud_dispatch_request takes request_id, rechecks packet freshness/readiness, acquires the existing execution lease and changes phase to requested. Only then should the parent create exactly one supported cloud task. Include request_id and packet digest in the task prompt. If creation times out or has an uncertain response, do not create again. cloud_dispatch_reconcile with status unknown persists reconciling; the parent must find/read the correlated task or establish a confirmed non-creation before preparing another request. Local client_key idempotence does not make the external cloud creation API idempotent.

cloud_dispatch_bind, cloud_dispatch_heartbeat and cloud_dispatch_reconcile accept request_id and observation:{status,thread_id?,turn_id?,source_ref,tool_name,observed_at}. Use the exact IDs from the supported tool response and its evidence reference, with tool_name cloud_threads.<actual operation>. Store no credentials, access tokens or arbitrary raw responses. Observations are created, running, unknown, completed, failed, cancelled or not_created. A created task remains requested until running is observed; running changes phase to started. Missing turn IDs remain missing. Different identities, older observations and conflicting terminal observations reject. The local lease session_ref is explicitly dispatch-request:<local request UUID>, a correlation key, never a fabricated remote thread ID.

cloud_dispatch_cancel records reason and cancellation_requested, then waits in reconciling. It neither sends cancellation nor claims the task stopped. Parent uses the supported platform cancellation operation; only a subsequent observed cancelled/not_created result closes ownership. Remote completed closes the lease and returns the step pending; it does not pass any criterion. Failed or cancelled work cannot reuse acceptance. Unknown creation and generation drift stay owned/reconciling; neither automatically launches replacement work. A generation-drift observation records recovery required without changing newer step state. Cloud ownership remains held when local observations become stale; the reaper changes the request to reconciling without closing its lease or making its step claimable. Local deadlines and missing-artifact timers do not prove remote cancellation.

cloud_dispatch_submit requires confirmed remote completed, the current work generation, report_source_ref and a valid local completion_payload. It records the observed report as a fresh submission, leaving pending_review. Do not prepare another run while completed work awaits evidence/review; use explicit redo for legitimate new work. There is no cloud_dispatch_accept CLI command. Trusted orchestrator acceptance uses Store.acceptCompletion with its opaque capability after independently reviewing the actual report and evidence. Worker names, IDs, completed statuses and fixture hashes do not grant acceptance.

If independent QA finds a criterion failure in a submitted result, use the trusted `requestCompletionRevision` Store method with the exact submission identity and criterion feedback. The next cloud preparation uses a new stable client key and the same grant, goal, context, owned paths, and result evidence contract. Its packet includes the review feedback. Later incidental failures do not erase the review or relax the retry scope. Preparation leaves the new request unclaimed for the parent to handle through the normal dispatch lifecycle.

## Trust and validation

Observation validation establishes shape, identity consistency, freshness and correlation. It cannot independently authenticate a remote platform response: the trusted parent must obtain it from its authorized tools and attach a traceable source reference. Arbitrary local JavaScript/SQLite access is not a security boundary. Do not expose parent observation operations as worker authority, and never translate a platform denial into a different execution route.

Tests use mock cloud identities and an isolated database to verify lifecycle bookkeeping. Live work requires evidence of the actual task identity, supported tool results, command outcomes, limitations and independent acceptance.

## Supported result evidence (opt-in contract)

New jobs may use result_evidence_contract version 1, kind sha256_fixture, input_path relative to the isolated project root, observability_policy supported_task_outputs_only, raw_trace_required false, side_effect_assertion unseen_activity_not_verified. Its mandatory criteria are observable_artifact_result, observed_task_identity, and declared_scope_and_visibility_limits. This contract is deliberately narrower than proving the worker read mechanism or absence of unseen side effects. Existing contracts are not migrated or weakened.

After actual parent-observed completion, cloud_dispatch_capture_result accepts request_id, result_data {source_path,sha256,byte_count,content_marker,limitations}, result_source_ref, result_message_id, and visibility {mode:task_outputs_only,raw_worker_trace_available:false}. It independently reads the bounded local fixture, compares facts, and writes an immutable hashed receipt under evidence/. It returns a completion_payload but neither submits nor accepts it. Repeated identical captures reuse the receipt; conflicting captures reject. Source containment, generation, contract, packet, task identity, scope and receipt bindings are checked.

Submit through cloud_dispatch_submit, then have the independent reviewer call cloud_dispatch_verify_result with request_id, receipt_path and receipt_sha256 from the receipt {path,sha256} returned by capture. The verifier rechecks the current local file and receipt bindings, including explicit visibility limits. Only the trusted orchestrator capability can accept the submitted evidence after reviewing the authentic supported parent observations. A worker cannot accept its own report. Receipt hashes and asserted observation fields alone do not authenticate platform responses.

Authorization retains the actual human quote and its source separately from parent-derived delegation and constraints. Additional user authorizations retain separate source references; delegation must never be presented as a verbatim human instruction.


## Parent observation staleness and legacy lease recovery

Local heartbeat freshness is distinct from remote task liveness. For requested/started/reconciling cloud dispatches, stale-heartbeat, artifact and local deadline checks retain the open lease and work generation, mark reconciling and append an ownership_hold event. This includes uncertain admission with no identity: only actual not_created reconciliation may release it. Ordinary local leases still use bounded stale recovery. No one-minute polling is required to preserve cloud ownership. Parent reads can occur at useful checkpoints; missing observations remain explicitly unknown.

Unresolved cloud ownership also blocks ordinary claim_step, next_step/ready_steps frontiers and unrelated open_execution_lease calls, including legacy requests whose local lease was already reaped. A completed observation does not accept criteria, and cancellation intent never proves a remote stop. No status field alone permits relaunch.

cloud_dispatch_recover takes request_id, reason and a real supported observation. It requires an existing exact thread and turn, a prior reap: closure, current work generation and unchanged packet scope/context/contract. For a historical running/created observation it opens only a replacement local ownership lease for the SAME remote task, preserves the old closed row/history, records the observation's actual historical timestamp and remains reconciling. It never launches or fabricates current liveness. For an actual completed/failed/cancelled observation it reconciles the terminal outcome without creating a replacement lease, preserving the old local cancellation audit and recording closed_lease_terminal_recovery. Newer work/scope or mismatched identities are rejected rather than overwritten.

Partial software results may be preserved as hashed artifacts with source references and per-criterion blockers in append-only notes. They are not strict validated completion submissions. cloud_dispatch_submit still requires all mandatory verified evidence; it cannot turn a partial/UI-blocked result into acceptance. The independent reviewer must evaluate actual artifacts and supported parent observations. Old already-loaded servers retain their old reaper code until refreshed; the new ordinary claim guards and explicit recovery protect against blind replacement in fresh ledger processes, but stale hosts must not be relied upon for the updated lifecycle.


Running ownership recovery uses a separate non-serializable constructor capability: trusted wiring constructs Store(dbPath,{cloudOwnershipAuthority}) and passes that exact object to recoverCloudDispatch(store,args,{cloudOwnershipAuthority}). The bridge passes it as a separate internal argument to openExecutionLease. Caller-supplied executor labels, metadata, JSON-shaped tokens or request IDs never authorize an exemption. Ordinary CLI/MCP open_execution_lease has no capability path. CLI cloud_dispatch_recover alone receives the privately wired object after the bridge validates exact identity, observation provenance, current generation, prior reap closure and packet freshness. Arbitrary privileged same-process JavaScript/source/SQLite remains outside this application capability boundary; the parent authenticates platform observations.
